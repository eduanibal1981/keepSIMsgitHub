## Admin credential control contract

The requested admin screen is a write-only replacement interface. A power user supplies a replacement that was provisioned with the provider; `admin_rotate_provider_credential` stores it in the allowlisted named Vault entry and records metadata. `admin_list_provider_credentials` exposes configuration/rotation metadata, never the current or previous secret. The existing `admin_set_vault_secret` convention already calls `assert_admin()`, pins an empty search path, returns a Vault UUID and records a metadata-only audit event; the new provider-specific contract must preserve those boundaries and restrict the accepted credential names.

The UI describes a successful write as `stored_pending_external_verification`, with `requires_external_sync: true`. After the operator verifies every consumer, recovery and old-key revocation, the version-checked completion action records `operator_confirmed`. This is a human attestation, not an automatic provider check; each subsequent replacement returns to pending. It must not claim that the provider accepted a new credential, an Edge environment changed, workers reloaded or the old provider credential was revoked. Supabase management PATs and the admin application's own service-role/management authority must not be stored or used in Flutter. Ordinary-user, anonymous and unauthenticated requests must be denied by the server even if a client route is bypassed.

Keep replacement input obscured, empty on entry and cleared after submission/disposal; avoid local persistence, request/body logging and displaying the input again in errors. Metadata refresh must not fetch secret values. Use a reason, expected version and server authorization/concurrency checks where supported by the final RPC. Rotation metadata is evidence of storage, while provider verification and external synchronization need their own operator record.

Vault-first resolution supports the complete listed local Edge consumers after their compatible code release. The deployed versions, Node workers, personal tools and Coturn may still have their own environment/configuration consumers. The operation remains incomplete until all required external consumers are synchronized, verified and old credentials are revoked. Document a provider-side maintenance window where the provider has immediate invalidation or where the current single-secret consumer cannot overlap safely.

The requested local macOS artifact is `../keep_sims_admin/build/macos/Build/Products/Release/keep_sims_admin.app`, built for Apple silicon and Intel with a macOS 12.0 minimum. Local validation recorded an ad hoc signature and successful startup. That establishes a launchable local application and the prepared UI; it does not establish notarized distribution, an authorized production credential replacement, a deployed RPC or provider revocation. Keep the signed-in power-user/ordinary-user release checks below pending until the backend release is authorized.

## Authorized operational release checklist

This is a concrete runbook to execute only after an operational scope is approved. Current task authorization covers preparing the code, macOS app and this checklist; it does not authorize these provider changes or production deployment.

1. Record the account owner, intended project, provider environment, existing consumer names, release artifacts, operator and maintenance window. Confirm sandbox versus production in each provider console; do not infer it from a literal or filename. Review pending/active calls, refills and refunds before pausing affected submission paths. Preserve in-flight state and callbacks.
2. Release the reviewed allowlisted credential RPC migration and corrected Edge/client code using a targeted deployment list. Verify RPC grants and ordinary-user denial. Do not run an unfiltered migration push: the pending financial queue contains unrelated changes. Firsty stays undeployed.
3. Provision replacement credentials through each provider's supported administration surface, following the provider-specific ordering below. Use the write-only admin screen for the allowed provider Vault entries. Supply other consumer environments through their protected deployment secret mechanism, without pasting values into commands, shell history, tracked files or chat.
4. Synchronize every consumer in the matrix. Resolve legacy environment aliases and any environment value that overrides the intended store. Once all legacy readers have been migrated and verified, remove secret-bearing plaintext `system_configs` values through a scoped forward cleanup. Do not remove identifiers or working consumer configuration prematurely.
5. Reload only the affected Edge/worker/Coturn processes using their approved release procedure. Worker source authority is `../backend-sync-wt`; VM source is copied directly to `/home/abdal/keepsims_backend/servers/`. An environment file write alone does not prove running PM2 processes loaded it. Check sanitized names/presence and non-sensitive startup/heartbeat evidence, avoiding `pm2 env`, raw process-environment output or dumping the whole configuration.
6. Verify the new credential using provider authentication or a non-spending read-only metadata request, with bodies/tokens suppressed. Verify affected webhook signatures with controlled fixtures and then real accepted/rejected callback evidence in the approved scope. Do not use a real top-up, eSIM order, call, SMS, payout or refund as a casual credential test.
7. Revoke/disable the exposed credential at its issuing authority; explicitly verify the old credential no longer authenticates using a controlled non-spending request with secrets withheld. Keep a metadata-only revocation record. A new Vault value alone is not revocation.
8. Resume the affected permitted traffic, inspect errors and reconciliation queues, and record each consumer's deployed version/configuration generation. If verification fails, pause new affected operations and repair the new credential/configuration. Do not silently reinstate a credential known to have been embedded in source or client binaries.
9. Clean/rebuild generated artifacts and scan distributable customer/admin packages. Coordinate Git history/fork/cache cleanup and tell holders of old tool config to remove it after revocation. Retain an exposure register recording unresolved copies; source deletion alone never closes it.

## Repeatable local scan

The focused regression scanner prints only `CATEGORY repository/path:line:rule`; it never prints matching source lines or credential values. The default scans tracked and nonignored files in the customer, admin and authoritative worker repositories. Ignored `.env` files and dependency directories are outside that embedded-source gate. Public anonymous/publishable keys, explicit placeholders, metadata identifiers and short synthetic test fixtures are excluded; known provider credential formats are checked even in fixture paths. Binary/build/history inspection remains a separate inventory. This scanner detects the reported families and common literal assignments/fallbacks; it is not proof that arbitrary unknown provider credentials or obfuscated values are absent.

```sh
python3 -m unittest discover -s tools -p 'test_scan_embedded_secrets.py' -v
python3 tools/scan_embedded_secrets.py
python3 tools/scan_embedded_secrets.py --include-generated
python3 tools/scan_embedded_secrets.py --include-history
```

The completed focused scanner regression suite passed 10 tests. The active-source scan across the three local repositories reported zero active findings, one archived SQL finding, zero oversized working-tree files and 115 active binary files skipped. The all-reachable-history inventory reported 87 historical rule/locations in addition to that archived finding. These counts are locations/rules, not distinct usable credentials or evidence that the credentials are still valid.

Active-source findings fail with exit status 1. Archived, generated and historical findings are reported as outstanding exposure inventory without failing the source gate; `--fail-on-inventory` makes those findings fail too. Exit status 2 means the requested scan did not complete. Files over 150 MB are skipped and counted for working-tree scans; confirm release archives separately. Active binary files detected by NUL bytes in their initial 8 KB are skipped and counted. Optional generated binaries receive the fixed provider-format/predictable-secret checks, not text-assignment parsing or archive decompression. History scanning considers reachable Git objects up to the same size cap, not deleted unreachable objects, remote-only refs or other machines; the summary's size counter applies to working-tree files. The CI workflow runs the scanner tests and scans only the checked-out repository with `--repo .`, so absent sibling repositories do not cause CI failures. Local default scanning still covers all three repositories when present.
