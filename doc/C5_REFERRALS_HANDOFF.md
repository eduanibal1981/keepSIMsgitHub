## Owner decision (encoded in plan — confirm arithmetic in-session before coding)

Points system. A referred user's line subscribed to **Standard or Premium** earns the
referrer **1 point per subscribed line**; **10 points = $2.00** wallet credit, converted
only via an explicit redemption. Aggregation across referred users (10 users × 1 line or
1 user × 10 lines both qualify). Points awarded once, **no clawback** on
downgrade/cancel (confirm). Blocking confirm-with-user items (plan line ~1116): the
points math and the no-clawback rule.

  `handle_new_user`, populated for all 8 users. **`profiles.referred_by`** (text code)
  exists, nullable.
- **`referrals` table exists in the OLD shape** — `(id, referrer_id, referred_id,
  referral_code, reward_amount, referrer_credited, referred_credited, created_at)` —
  and holds **0 rows**. Safe to reshape/recreate.

  fails with permission-denied today. Nobody has ever applied a code (0 rows).
- **Its economics contradict C5**: it credits **$2.00 to BOTH referrer and referred
  instantly on code application** (no subscription required) via `credit_wallet`. Under
  the C5 points model this whole payout path is superseded.
- **`lib/features/referrals/` already exists** (contract/model/repository/controller/
  screen, routed in `app_router.dart`): freezed `Referral` matches the OLD table shape;
  the screen is "SIM Shield"-era with **hardcoded English strings** (no ARB) and a
  **simulated** share sheet. Salvageable skeleton, wrong data model and wrong copy
  (promises instant rewards).
- **Wallet plumbing is ready**: `credit_wallet` exists; `'referral_credit'` is already
  in the `wallet_transactions.type` CHECK; `wallet_transactions` has `sim_line_id`,
  `reference_id`, `metadata`. **No idempotency index for `referral_credit`** — the
  partial unique indexes on `reference_id` cover only `topup_debit`/`refund` (B2
  pattern); redemption needs its own.
- **Notifications ready**: `referral_reward` is one of the canonical 12 categories
  (C2), so the C1 dispatcher fans out with zero new wiring.
- **`sim_lines.plan_type`** ∈ free/standard/premium in practice but has **NO CHECK
  constraint** and is **client-writable** (owner RLS UPDATE). ⇒ `plan_type` transitions
  are NOT a trustworthy award signal — a user could mint points by toggling a column.
- **The two server-authored payment surfaces** (C3c) are the only trustworthy signals:
  - Wallet path: `pay_plan_fee_from_wallet` → ledger row `type='plan_fee_debit'`
    **with `sim_line_id`**. ✅ usable as-is.
  - PayPal path: `paypal-webhook` v6 → `plan_payments` insert (kind='plan'). ⚠️
    **`plan_payments` has NO `sim_line_id` column** (only `metadata` jsonb; custom_id
    carries `{u,k}` only). Gap must be closed for PayPal-paid plans to award points.
- **None of the plan's C5 tables exist** (`referral_codes`, `referral_points`,
  `referral_redemptions`). `plan_payments` exists (C3c).

## Design conflicts & judgment calls (recommendations)

1. **Replace `apply_referral`, don't reuse** (plan item 4 says decide deliberately —
   decided: replace). It's unreachable, and its instant-$2×2 payout is a live money
   faucet the moment anyone re-grants EXECUTE. Rewrite it in place (same name keeps the
   client call site) with the old validations (normalize UPPER/TRIM, invalid code,
   self-referral, already-referred) but **no wallet credits** — it only records
   `profiles.referred_by` + a `referrals` row. GRANT authenticated (self-scoped, like
   `request_instant_refill`).
2. **Skip the `referral_codes` table** (deviation from plan sketch item 1):
   `profiles.referral_code` is already unique, indexed, and generated for every user by
   `handle_new_user`. A second table is pure drift risk. Record the deviation in the
   plan.
3. **Award trigger hooks the money trail, not `plan_type`**: AFTER INSERT on
   `wallet_transactions` (`type='plan_fee_debit'`, `sim_line_id IS NOT NULL`) + AFTER
   INSERT on `plan_payments` (`kind='plan'`). Award fn resolves line owner →
   `referred_by` → referrer, inserts 1 point `ON CONFLICT (sim_line_id) DO NOTHING`
   (UNIQUE on `sim_line_id` = the plan's double-count guard; also makes renewals award
   nothing — first qualifying payment only, matching no-clawback symmetry).
4. **Close the `plan_payments` gap**: add `sim_line_id uuid` column; extend the PayPal
   `custom_id` payload `{u,k}` → `{u,k,l}` at the plan-charge call sites and have
   `paypal-webhook` (v7) write it. Backward compatible — missing `l` ⇒ NULL ⇒ no award
   (webhook must not break on old orders in flight). Edge Fn redeploy gotcha: pass
   `import_map_path: "deno.json"` + include `deno.json` (`{}`) or MCP deploy fails.
5. **Redemption RPC** `redeem_referral_points()` — SECURITY DEFINER, authenticated,
   self-scoped: lock, balance = Σpoints − Σpoints_spent, require ≥10, insert
   `referral_redemptions(10, wallet_txn_id)`, `credit_wallet` $2.00
   type `referral_credit` reference `refredeem_<uuid>`; add the **partial unique index
   on `reference_id` WHERE type='referral_credit'** (same idempotency pattern as B2).
   Never from the client — client writes to all three new tables revoked, read-own RLS.
6. **Abuse controls** (plan item 6): self-referral block kept; `referred_by` immutable
   once set (already enforced by the already-referred check — keep it in the rewrite);
   daily award cap per referrer via `system_configs.REFERRAL_DAILY_POINT_CAP`
   (DB-tunable per the house rule; suggest 10), excess events dropped + logged to
   `system_alerts`. Same-device heuristic: **skip** — no device-fingerprint infra
   exists and the farming economics don't pay (a point costs the referred user a real
   $2.50 plan fee; $2 per 10 points ⇒ farming loses ~$23 per redemption). Note the
   skip in the plan.
7. **UI rebuild, not restyle**: new freezed models (points summary, history), progress
   to next $2, redeem button (disabled <10), referred-friends list, redemption history,
   copy-code + real share (check pubspec for share_plus; else clipboard). Replace ALL
   hardcoded strings with ARB ×9. The old screen's "instant reward" copy must die with
   the old model.
